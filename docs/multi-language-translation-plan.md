# MkDocs Translator 英、日、韩多语言支持方案

## 1. 背景与目标

当前项目用于将中文 MkDocs 文档翻译为英文。虽然命令行已经提供 `--target-language` 参数，但提示词、术语表、标点规则、英文复数规则和中文残留校验都按照英文翻译写死，增量翻译状态也没有目标语言维度。

本次计划在当前 `feature/multi-lang` 分支上增加英语、日语、韩语支持，并保持以下使用方式：

- 中文始终为源语言。
- 同时支持一次命令翻译一种或多种目标语言。
- 单语言模式下，`--target` 继续表示该语言的实际输出目录。
- 多语言模式下，`--target` 表示多语言根目录，译文写入其下的 `en/`、`ja/`、`ko/` 子目录。
- 保持现有英文调用方式兼容。
- 不在本次工作中合并 `feature/remove-dify` 的段落级缓存实现。

现有单语言调用保持不变：

```bash
mkdocs-translator --source docs/zh --target docs/en --target-language en
```

新增一次运行多种语言的调用方式：

```bash
mkdocs-translator --source docs/zh --target docs --target-languages en,ja,ko
```

上述多语言命令输出：

```text
docs/
├── en/
├── ja/
└── ko/
```

## 2. 当前实现的主要问题

### 2.1 提示词实际只适用于英文

当前公共提示词包含以下英文专属要求：

- 强制使用英文半角标点。
- 单独的中文名词翻译成英文时使用复数。
- 整份术语表只有英文译法。
- 翻译角色和示例均以中译英为前提。

如果直接将目标语言改成日语或韩语，这些规则会造成语言风格错误和术语混用。

### 2.2 增量状态会在语言之间相互污染

当前 `metadata.json` 和 `last-metadata.json` 保存在中文源目录，文件记录只包含源文件 hash 和成功状态，不包含目标语言。

因此，英文完成后再运行日语或韩语时，相同的中文源文件可能会被误判为已经翻译。此外，目标文件被删除后，只要源文件 hash 未变化，当前逻辑仍可能跳过翻译。

### 2.3 中文残留检查不适用于日语

当前 `--check-chinese` 通过 Unicode 汉字区间判断译文中是否存在中文字符。日语正常使用汉字，因此该检查会把合法日语内容判定为翻译失败。

### 2.4 并发状态写入存在风险

多个 worker 共用同一个元数据对象并直接覆盖同一个 JSON 文件，没有线程锁和原子写入保护，可能产生状态丢失或 JSON 文件损坏。

### 2.5 控制文件可能被当作资源复制

当前资源复制逻辑只排除 Markdown 和 `.pages`，源目录中的翻译元数据、黑名单和其他控制文件可能被复制到目标目录。资源清理也需要显式保护翻译器自己的状态目录。

## 3. 命令行接口

### 3.1 目标语言

`--target-language` 和 `--target-languages` 正式支持三个标准语言代码：

| 标准代码 | 语言 | 兼容别名 |
| --- | --- | --- |
| `en` | 英语 | `English`、`英语`、`英文` |
| `ja` | 日语 | `Japanese`、`日语`、`日文` |
| `ko` | 韩语 | `Korean`、`韩语`、`韩文` |

别名匹配时忽略大小写并清理首尾空白，进入核心逻辑前统一转换成标准代码。未知语言必须在调用模型 API 前报错。

- `--target-language LANGUAGE`：单语言兼容模式，`--target` 是该语言的实际目录。
- `--target-languages LANGUAGES`：多语言模式，接收逗号分隔的语言列表，`--target` 是多语言根目录。
- 两个参数互斥且必须提供其中一个。
- 多语言列表保持用户指定顺序并自动去重，允许 `en,ja`、`ja,ko` 或单元素列表。
- 多语言模式的目标目录固定为 `<target>/<标准语言代码>/`，不使用别名作为目录名。
- 语言子目录不存在时自动创建；已经存在时原地复用，不删除、不清空。只有新译文通过校验后才替换对应文件。
- 所有目标语言目录必须在写入前解析真实路径并完成安全检查：不得等于源目录、不得位于源目录内部，不同语言目录不得解析到同一路径。

### 3.2 术语表参数

新增可选参数：

```text
--glossary PATH
```

该参数用于覆盖或补充项目内置的多语言术语表。未提供时只使用内置术语表。

### 3.3 现有检查参数

保留 `--check-chinese`，但根据目标语言执行不同逻辑：

- 英语、韩语：启用时检查可翻译正文是否残留汉字。
- 日语：不执行汉字残留判断，并记录说明日志；仍执行 Markdown/YAML 结构检查。

保留 `--check-line-count` 的现有 5% 行数差异规则，适用于所有目标语言。

`--workers` 必须大于等于 `1`，非法值在任务启动前报错。

### 3.4 多语言任务模型与并发

最小执行任务定义为一个 `(目标语言, 源文件)` 组合。假设有 10 个待翻译文档和 `en,ja,ko` 三种目标语言，候选任务总数为 30；`--workers 10` 只创建 10 个 worker，由这 10 个 worker 从统一队列消费 30 个任务，不会为每个任务或每种语言额外创建 worker。

执行前按以下顺序准备任务：

1. 一次性验证所有目标语言、目标目录、API 配置、prompt 和术语表；任一全局配置无效时不启动任何翻译。
2. 为每种目标语言创建独立的语言 profile、translator、目标目录和 MetadataManager。
3. 先完成各目标目录的资源同步；英文目标目录在此阶段执行旧 metadata 首次迁移。
4. 对每个 `(语言, 文件)` 独立执行增量判断。无需翻译的组合计入该语言的 skipped 数量，不进入任务队列。
5. 按“源文件优先、语言次序”的顺序生成待翻译任务，例如 `doc1/en`、`doc1/ja`、`doc1/ko`、`doc2/en`。线程池实际完成顺序无需保证。
6. 使用一个全局线程池，`max_workers = min(--workers, 待翻译任务数)`。每个 worker 任一时刻只处理一个 `(语言, 文件)` 任务，所有语言共享同一个并发上限。

实现采用固定数量的长生命周期 worker 从统一队列领取任务，每个 worker 拥有稳定的进度槽，并按实际处理语言延迟创建自己的 Translator/API 客户端。不能使用“任务序号取模”假定任务会落到某个真实线程；进度状态由 CLI 层统一维护，不保存在 Translator 中。

不同语言的任务允许同时执行，但最大模型请求并发数始终不超过 `--workers`。例如 30 个任务和 10 个 worker 最多只有 10 个请求并发，而不是 30 个。

每种语言的 metadata 使用独立线程锁和原子写入。任务失败只影响对应的 `(语言, 文件)`，不阻塞队列中的其他语言或文件；所有任务结束后，只要存在任一失败，CLI 返回非零退出码。

进度显示包含一个总进度和分语言计数，worker 当前任务带语言前缀，例如 `[ja] guide/index.md`。最终输出每种语言的 success、failed、skipped 以及全部语言的汇总结果。

## 4. 语言配置层

新增统一的 `LanguageProfile` 配置模型，至少包含：

- 标准语言代码。
- 可接受的语言别名。
- 提供给模型的目标语言名称。
- 语言专属翻译风格和标点要求。
- 是否支持汉字残留检查。
- 语言配置版本，用于增量状态失效判断。

三个首批语言的默认规则如下：

### 4.1 英语

- 使用专业、简洁的可观测性技术文档风格。
- 使用英文半角标点。
- 保留现有英文名词复数要求。
- 启用 `--check-chinese` 时检查正文中的残留汉字。

### 4.2 日语

- 使用正式技术文档的 `です・ます` 风格。
- 使用符合日语习惯的标点，不继承英文标点要求。
- 不继承英文名词复数规则。
- 允许合法日语汉字，不使用 Unicode 汉字区间判断翻译是否完成。

### 4.3 韩语

- 使用正式技术文档的 `합니다` 风格。
- 使用符合韩语技术文档习惯的标点。
- 不继承英文名词复数规则。
- 启用 `--check-chinese` 时检查正文中的残留汉字。

## 5. 提示词重构

翻译提示词拆分为三部分，在每次请求前动态组合：

1. 公共结构规则。
2. 当前目标语言的专属规则。
3. 当前目标语言的有效术语表。

公共规则负责：

- 不增加、删除或扩展原文内容。
- 保持 Markdown 标题、列表、链接、图片、加粗和斜体语法。
- 保持代码围栏、HTML 标签、注释和空行。
- 保持 `<<< >>>` 模板变量不变。
- 保持 YAML 数据结构和路径类字段。
- 输出中不附加 XML 标签、代码块包装或解释性文字。

英文复数、英文标点等规则只能存在于英语 profile 中，不得进入日语和韩语提示词。

最终文件职责固定如下，禁止维护重复词典：

- `mkdocs_translator/data/terminology.yml`：唯一的内置中英日韩术语源。
- `mkdocs_translator/terminology.py`：读取、校验、合并自定义词典。
- `mkdocs_translator/prompts.py`：公共规则、语言规则和 Prompt 动态组装。
- `mkdocs_translator/multilingual_prompts.py`：只保留旧准备模块的兼容导出，不得再次定义术语。

## 6. 多语言术语表

### 6.1 文件格式

内置和自定义术语表都使用 YAML：

```yaml
version: 2
terms:
  观测云:
    en: Guance
    ja: Guance
    ko: Guance
  应用性能监测:
    en:
      full: Application Performance Monitoring
      short: APM
    ja:
      full: アプリケーションパフォーマンスモニタリング
      short: APM
    ko:
      full: 애플리케이션 성능 모니터링
      short: APM
    usage: first_mention
    ui: short
  查看器:
    en: Explorer
    ja: エクスプローラー
    ko: 탐색기
```

### 6.2 合并与使用规则

- 现有英文硬编码术语全部迁移到内置 YAML。
- Guance、APM、RUM、DataKit、云厂商名称等稳定品牌或行业缩写可在三种语言中保持一致。
- 普通固定词条兼容 `version: 1`；需要区分全称和缩写的概念词使用 `version: 2`。
- `first_mention` 概念词在每篇文档首次出现中文全称时输出“全称（缩写）”，后续使用缩写；紧凑 UI 使用 `ui` 指定的形式。
- 自定义词表按中文源词合并内置词表，相同语言的自定义值优先。
- 每次任务只把当前目标语言的词条注入提示词。
- 当前目标语言缺少译法时，将该词交给模型翻译，并在任务开始时汇总记录一次告警。
- 词表格式错误、语言字段拼写错误或值类型错误时，任务启动失败，避免静默使用错误配置。

## 7. 增量状态设计

### 7.1 存储位置

停止在中文源目录中写入运行状态。每个目标目录维护自己的状态：

```text
目标目录/
├── 翻译后的文档和资源
└── .mkdocs-translator/
    ├── metadata.json
    └── last-run.json
```

因为每种语言使用不同目标目录，状态天然按语言隔离。

### 7.2 元数据结构

```json
{
  "version": 2,
  "target_language": "en",
  "translation_fingerprint": "sha256-value",
  "legacy_migration": {
    "completed": true,
    "migrated_at": "2026-01-01T00:00:00",
    "imported_files": 20
  },
  "files": {
    "guide/index.md": {
      "source_hash": "sha256-value",
      "last_translated": "2026-01-01T00:00:00",
      "translation_time": 1.5,
      "status": "success"
    }
  }
}
```

`translation_fingerprint` 由以下内容生成：

- 标准目标语言代码。
- 语言 profile 版本。
- 公共及语言专属提示词版本。
- 当前语言实际生效的术语表。

模型名称和 API 地址不进入 fingerprint。Prompt、术语表、模型和 API 地址的变化均不会自动触发已有文档重新翻译。

fingerprint 使用稳定 JSON 序列化后计算 SHA-256：包含标准语言代码、语言 profile 版本、Prompt 版本，以及按中文源词排序的当前语言有效术语。该值保存在运行状态和文件记录中，仅用于审计当时使用的翻译配置，不参与增量翻译判断。

### 7.3 增量判断

文件只有同时满足以下条件才允许跳过：

- 元数据语言与本次目标语言一致。
- 文件上次状态为 `success`。
- 当前中文源文件 hash 与记录一致。
- 目标译文文件仍然存在。

任意条件不满足都需要重新翻译。

Prompt、专业词典、模型或 API 配置发生变化时，不会使已有成功译文失效。需要应用新词典的历史文档，应修改对应中文源文件，或删除对应目标译文后重新运行。

如果目标目录已经绑定其他目标语言，任务必须失败并提示使用新的目标目录，禁止不同语言相互覆盖。

### 7.4 旧英文状态迁移

这里的迁移是“读取旧状态、验证后转换写入新状态”，不是移动或删除源目录中的旧文件。

迁移只在以下条件全部成立时自动执行：

- 本次标准目标语言为 `en`。根据旧版项目用途和 README，源目录旧 metadata 只按英文状态处理。
- 英文目标目录中的 `.mkdocs-translator/metadata.json` 尚不存在。
- 中文源目录中存在可读取、格式有效的旧 `metadata.json`。

迁移流程固定如下：

1. 以只读方式加载中文源目录的旧 `metadata.json`；JSON 损坏时记录告警并放弃迁移，按首次翻译处理，不能覆盖或修复旧文件。
2. 逐条规范化旧记录的相对路径，拒绝绝对路径、`..` 越界路径以及源目录中已经不存在的文件。
3. 只导入旧状态为 `success`、旧 hash 与当前中文源文件一致、对应英文目标文件确实存在的记录。
4. 旧失败记录、hash 已变化记录和目标译文缺失记录不导入，由本次任务正常重新翻译。
5. 将通过验证的记录转换为新版 `files` 结构，写入目标目录 `.mkdocs-translator/metadata.json`，同时写入 `target_language: en`、当前 translation fingerprint 和 `legacy_migration` 摘要。
6. 新 metadata 通过临时文件和原子替换一次性提交；提交失败时不得留下半份迁移状态。
7. 迁移完成后立即按新版增量规则再次判断文件。后续 Prompt 或英文术语表变化不会触发导入记录重新翻译。

迁移具有幂等性：只要目标目录中的新版 metadata 已存在，后续运行就不再读取旧 metadata。即使首次迁移导入 0 个文件，也要写入完成标记，避免每次重复尝试。

旧 `last-metadata.json` 不迁移，因为它只是某次历史运行报告；源目录中的旧 `metadata.json` 和 `last-metadata.json` 均不删除、不修改，便于回滚和审计。资源复制时必须排除这两个文件。

日语和韩语不得导入无法确认目标语言的旧状态，首次运行直接在各自目标目录建立独立 metadata。

### 7.5 并发安全

- 元数据对象的更新和保存使用线程锁保护。
- JSON 先写同目录临时文件，再通过原子替换提交。
- `last-run.json` 在任务结束时统一生成，记录本次语言、成功/失败文件、耗时、token 使用和错误信息。
- 一次多语言运行共享同一个 `run_id`，但每个目标语言目录的 `last-run.json` 只记录本语言结果；全部语言汇总只输出到 CLI。
- 流式端点没有返回 usage 时，token 使用记录为 `null`，不得用 `0` 冒充准确统计。

## 8. 翻译结果校验与写入

所有语言都执行结构完整性校验：

- Markdown 代码围栏数量和边界保持一致。
- 链接和图片目标地址保持一致，显示文本允许翻译。
- HTML 标签名称、数量和顺序保持一致。
- `<<< >>>` 模板变量完整保留。
- `.pages` 译文仍可作为 YAML 解析，容器结构和路径类值保持一致。
- 启用 `--check-line-count` 时执行行数差异检查。

英语和韩语在启用 `--check-chinese` 时，只扫描可翻译正文；代码、URL、HTML 标签和模板变量等受保护区域不作为残留中文判断依据。

翻译结果不得直接覆盖现有文件：

1. 将新译文写入目标目录中的临时文件。
2. 完成全部结构和语言检查。
3. 检查通过后原子替换正式目标文件。
4. 检查或翻译失败时删除临时文件，保留上一版有效译文。
5. 元数据记录为 `failed`，下一次运行继续重试。

目标文件和 metadata 的提交顺序固定为“临时译文 → 全部校验 → 原子替换目标文件 → 写入 success metadata”。如果替换后、metadata 提交前进程中止，下次允许保守地重新翻译，禁止出现 metadata 已成功但目标译文尚未提交的状态。

## 9. 资源同步

资源复制和失效资源删除必须排除以下控制内容：

- `.translate-blacklist`
- `metadata.json`
- `last-metadata.json`
- `.mkdocs-translator/`
- `.translation-cache/`
- 翻译日志和临时文件

除上述控制内容外，图片、CSS、JavaScript 和其他正常文档资源继续按照现有参数复制。

删除失效资源时不得进入或删除 `.mkdocs-translator` 状态目录。

新增显式的 `--delete-removed-translations`。默认保留中文源文档被删除或加入黑名单后遗留的译文；只有启用该参数时，才删除各语言中由 metadata 管理的孤立 `.md`/`.pages` 译文及对应记录。该行为与 `--delete-removed-resources` 相互独立。

任务列表在生成语言组合前按相对 POSIX 路径排序。没有待翻译任务时不创建线程池并以 `0` 退出；任务失败以 `1` 退出；命令行、词典和路径预检错误以 `2` 退出；用户中断时停止领取新任务、保存已完成状态并以 `130` 退出。

## 10. 测试计划

现有测试脚本主要打印结果，部分测试仍向 `DocumentTranslator` 传入已经不存在的 `user`、`query` 参数。需要改造成具有真实断言、可自动执行的测试，并模拟 OpenAI 客户端，避免测试调用真实模型。

### 10.1 语言和提示词

- `en`、`ja`、`ko` 及所有兼容别名能正确规范化。
- 不支持的语言在 API 调用前失败。
- 英文半角标点和复数规则只进入英文提示词。
- 日语和韩语提示词包含各自正式文体规则。
- 三种提示词只注入对应语言的术语。

### 10.2 术语表

- 内置术语可以正常读取。
- 自定义术语按语言覆盖内置术语。
- 缺失译法只产生一次汇总告警并回退给模型。
- 错误的 YAML 结构会阻止任务启动。
- 只修改日语术语不会让英文状态失效。

### 10.3 增量状态

- 单次执行英语、日语、韩语时状态互不影响。
- 英语完成后不会导致日语和韩语被跳过。
- 源文件未变化且目标文件存在时正确跳过。
- 源文件变化、目标文件丢失或上次失败时重新翻译。
- 同一目标目录切换语言时失败。
- 旧英文 metadata 只迁移符合条件的成功记录。
- 多 worker 并发完成后 metadata 仍是完整有效的 JSON。
- 10 个文件和 3 种语言生成 30 个候选任务，`--workers 10` 时实际 worker 和最大模型并发均为 10。
- 部分 `(语言, 文件)` 已缓存时只将剩余组合放入队列，skipped 计数正确。
- 同一源文件的三种语言任务可并发完成，且分别写入正确目标目录和 metadata。
- 单个语言任务失败不取消其他任务，最终汇总和进程退出码正确。

### 10.4 校验与文件安全

- 日语译文中的合法汉字不会被判定为中文残留。
- 英语和韩语在启用检查后能发现正文中的中文残留。
- Markdown 链接、图片、代码块、HTML 和模板变量保持完整。
- `.pages` YAML 保持有效结构和路径。
- 校验失败时上一版目标文件不被覆盖或删除。
- 控制文件不会被复制为普通资源，状态目录不会被资源清理删除。

### 10.5 安装与文档

- 补齐包初始化文件和 YAML 包资源声明。
- 验证源码方式和安装后的 `mkdocs-translator` 命令都能读取内置术语表。
- README 增加英、日、韩调用示例、语言别名、术语配置、状态迁移和日语校验限制。

## 11. 验收标准

- 使用一次 `--target-languages en,ja,ko` 命令，能在目标根目录的 `en/`、`ja/`、`ko/` 中产生对应译文。
- 原有 `--target-language en` 单语言命令保持兼容。
- 三个目标目录拥有独立、可重复使用的增量状态。
- 未变化文档不会重复调用模型，修改后的文档能够重新翻译。
- 日语不会因正常汉字被误判失败。
- 语言提示规则和术语不会跨语言污染。
- `--workers N` 在单语言和多语言模式下都严格限制全局最大并发为 N，不按语言倍增。
- 多语言并发运行不会混淆目标文件或破坏任一语言的元数据。
- 翻译或校验失败不会损坏已有有效译文。
- 原有英文命令和语言别名继续可用。

## 12. 范围与后续兼容

本次不合并 `feature/remove-dify` 的段落级缓存代码，只在当前分支完成整文件级多语言支持。

未来合并段落级缓存时必须遵守以下约束：

- 缓存继续存放在各语言目标目录中。
- 缓存数据包含标准目标语言。
- 缓存有效性只由源内容、成功状态和目标译文是否存在决定；语言 profile 和术语 fingerprint 仅用于审计。
- 不允许不同语言复用同一段落译文缓存。
